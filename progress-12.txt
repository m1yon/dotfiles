- The inline rename offer fires ONLY on the existing-part "same as X" path AFTER `append_alias` was queued. It does NOT fire on first-contact (`is_new === true`) — newly created parts haven't accumulated alias data yet, and the user just named the part 30 seconds ago, so asking "want to rework?" would be friction. - The candidate-surfacing rule (only user-supplied phrasings + existing aliases) is the most-loaded discipline in slice 9. There's a strong temptation to be helpful by paraphrasing or synthesizing — for example, if the user said "wants me to double-check everything" and "the rechecker," a less-disciplined skill might propose "the double-checker" as a synthesis. **Refuse.** The PRD acceptance criterion is explicit: "Skill plays back the user's own language as candidates; never synthesizes." Even paraphrasing one user phrase is synthesis. Reflect verbatim only. If the user wants a synthesized name, they can speak it themselves — that's a fresh phrasing, which is allowed.
- The `pending_renames` map is small (typically 0 or 1 entries; rarely 2 for a chain) and is consumed only by the subagent's `part_ref` resolution. The skill atomically updates it alongside queueing the matching `rename_part` entry — don't decouple. Reading: `pending_renames[X] = Y` is true iff a `rename_part { old_title: X, new_title: Y }` entry exists in `pending_changes`. The map walks chains: `pending_renames[A] = B` and `pending_renames[B] = C` resolves a `part_ref: "A"` to `"C"`. Cycles in the map (e.g. `A → B → A`) are theoretically possible — slice 9 doesn't guard against them because the user would have to rename A → B mid-session, then immediately rename B → A, which is implausible.
